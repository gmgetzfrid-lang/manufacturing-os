> **Verified, corrected, and lowered to `HIGH`.** The mechanism is real and is

**Mechanism.** queueEmail() runs in the browser against the anon client bound to the ACTOR's session. It looks up notification_preferences for input.toUserId — another person. The only policy on that table is notif_prefs_own ... USING (user_id = auth.uid()). So for every recipient who is not the actor the SELECT returns zero rows with no error, prefs is null, prefs?.email_enabled === false is false, prefs?.digest_frequency === "never" is false, and shouldSendForEvent(null, …) short-circuits on `if (!prefs) return true`. The email is queued unconditionally. The drain never re-checks: app/api/notifications/send-queued/route.ts reads only email_notifications and posts straight to Resend, so there is no second gate. The new-drafting-request notification — the entry point of the whole flow — is emitted through exactly this path (requests/new/page.tsx:342 emit({category:'assignment', kind:'request_pending_approval'}) → dispatch.ts:116 queueEmail). The comment at dispatch.ts:105 asserts the opposite. The two server-side ticket routes prove the correct pattern exists (workflow-action/route.ts:351 and comment/route.ts:276 both read prefs with supabaseAdmin), so only the client-side emit() producers are blind.

**Failure scenario.** A DraftingSupervisor turns off 'Assignments' (or Email notifications entirely) on /settings/notifications because she works her queue through the portal. She still receives an email for every new drafting request filed by anyone in the org, forever, because the requester's browser cannot read her preference row. She filters the sender to spam — and the one email class that DOES honor her preference (a genuine engineering-review request routed server-side) now lands in the same filtered folder and is never seen. The settings page told her the switch worked; the code could never make it work.

- **Severity:** HIGH

- **Verification:** CONFIRMED
- **Locations:** `lib/dataRestore.ts:335-341`, `app/api/admin/restore/apply-table/route.ts:75-88`, `app/(protected)/admin/restore/page.tsx:193-207`, `supabase/schema.sql:444`, `supabase/schema.sql:495`, `supabase/migrations/20260724_ticket_numbering.sql:20-25`

The comment at `:335` describes exactly this class: *"upserting them on 'id' errors and breaks re-runnability."*
- **Independently verified:** ✓ **SURVIVES** — independent adversarial pass. All three clauses hold. **Mechanism.** Three interlocking facts. (1) tickets has both a uuid PK and UNIQUE(org_id, ticket_id) (schema.sql:444). conflictTargetFor('tickets') returns the default 'id' because CONFLICT_TARGETS lists no entry for tickets, so the upsert's ON CONFLICT clause cannot see a human-number collision; PostgREST attempts the insert and Postgres raises on the unique index. (2) apply-table's error path retries the identical chunk with a plain .insert() — the same violation — and returns 500. The client at restore/page.tsx:202 does `if (!res.ok) { tableFailed = true; break; }`, abandoning EVERY REMAINING CHUNK of that table while continuing to later tables; ticket_comments is ordered after tickets in RESTORE_TABLE_ORDER and has ticket_id UUID NOT NULL REFERENCES tickets(id), so its rows for the abandoned tickets then fail their FK too. (3) ticket_number_counters uses conflict target 'org_id,year' with ignoreDuplicates: true, so the target workspace's live counter is deliberately preserved — correct for a merge, fatal in combination: the restored tickets occupy human numbers the counter will hand out again.

**Failure scenario.** Two plants merge and an admin restores Plant B's backup into Plant A's workspace — the flow the confirm dialog explicitly supports ('Existing data is kept — this is additive'). ## EDGE-19 · A request renumbered on restore keeps its files under its old number's folder, so the request's own file checks treat them as outside the request

- **Severity:** MEDIUM
- **Status:** OPEN
- **Assigned:** drafting-flow (the owner of the request's file prefix checks, `app/api/tickets/**` and `lib/ticketCopyRequest.ts`) — opened by admin-and-org Round G P16 RESTORE TICKET NUMBER KEY's fix pass 3, 2026-10-21, from the package review, as the named remainder of `EDGE-5` ruling (4) and of `EDGE-18` done-when 1 (`DEC-31`: a remainder is a new id with an owner). The integrator may re-assign it.
- **Verification:** CONFIRMED by reading the code at the P16 fix pass 3 (`lib/ticketCopyRequest.ts:138`, `app/api/tickets/workflow-action/route.ts:183`); the restore side is pinned by `lib/__tests__/aoRoundGP16RestoreTicketNumber.test.ts` "a renumbered request's files keep their storage keys, under the old number's folder …"
- **Independently verified:** — (`author`: the P16 review found it; recorded by the P16 fix pass 3; not yet challenged)
- **Blast radius:** a request restored under a fresh number (`EDGE-5`, `TICKET_RENUMBERED`) — its Final, Source and redline files; and the request that keeps the old number (the holder), whose prefix checks accept those files as its own (*added at the P16 fix pass 4, from the review*)
- **Locations:**
  - `lib/ticketCopyRequest.ts:138` `ticketFileCopyPath` — the prefix is `orgs/<org>/tickets/<ticket number>/` from the request's CURRENT number, so a file under the old number's folder is `{ kind: "browser", reason: "outside_request" }` (no server-stamped, recorded copy)
  - `app/api/tickets/workflow-action/route.ts:183` `vetTicketAttachment` — `url.startsWith(prefix)` is checked BEFORE `alreadyListed`, so a `submit_final` or `redlineAttachment` naming one of the request's own listed files answers 400 "That file is not stored under this request"; on the HOLDER (the request keeping the old number) the same check passes for any key under `orgs/<org>/tickets/<old number>/`, and an unlisted key there is accepted (its size is read), so the renumbered request's files can be attached to the holder
  - `ticketKeyGate` (DF-P11) — signs a file for the readers of every request whose `attachments` list it, so a file attached to the holder is then signed for the holder's readers
  - `lib/dataRestore.ts` `renumberedTicketRow` — the restore records the old number (`metadata.restore_renumbered.from`) and, when one of the request's files sits in its folder, `metadata.restore_renumbered.files_kept_under` (`orgs/<org>/tickets/<old number>/`)
- **Related:** `EDGE-5` (ruling (3) re-mint, ruling (4), residual (e)), `EDGE-18` (the disaster-recovery case), admin-and-org `BKP-16` (the restore page's line)

**Mechanism.** A backup request whose number another request of the workspace already carries is restored under a fresh number (`EDGE-5` ruling (3)). Its `attachments[].url` keys are the backup's (moved to this workspace's `orgs/<id>/` only), so they sit under `orgs/<org>/tickets/<old number>/` — a folder that also belongs to the request that keeps the old number. "Put the files back" places each object at the key the backup has, so the files are there and the row points at them; but every check that derives the request's folder from its CURRENT number treats them as another request's files. Without the renumbering (`125ca3b`, a database without the key) the request kept the duplicate number and its files matched its prefix, so for such a request this is a functional change. The converse (*P16 fix pass 4, from the review*): the folder still belongs to the request that keeps the old number (the holder), whose prefix is `orgs/<org>/tickets/<old number>/`; `vetTicketAttachment` checks only `url.startsWith(prefix)` and accepts an unlisted key under it, so the holder's actors can attach the renumbered request's files as the holder's own, and `ticketKeyGate` then signs them for the holder's readers — including readers the renumbered request's own scope excludes. `125ca3b` shared the folder too (both requests carried the number), so this side is not a regression of the renumbering; it is the part of the shared folder the renumbering leaves, recorded here (`DEC-29`, `DEC-31`).

**Failure scenario.** A disaster-recovery backup carries `KE-DDRT-26-0007` on requests A and B; B has a Final and a Source file under `orgs/<org>/tickets/KE-DDRT-26-0007/`. After the restore B is `KE-DDRT-26-0123` with the same file keys. Printing or downloading one of B's files takes the browser path (no stamped, recorded copy), and resubmitting B's Final or redlining one of its files is refused "That file is not stored under this request". The holder side: a Contractor-only drafter on A, who knows a key under `orgs/<org>/tickets/KE-DDRT-26-0007/` that belongs to B, submits it as A's Final or a redline; the route accepts it, A now lists it, and the drafter downloads B's file although B's read scope excludes them.

**Remediation (for the owner to choose).** (a) The prefix checks also accept the folder of `metadata.restore_renumbered.from` (or exactly `files_kept_under`) for a file the request already lists — the restore wrote both, as the service role; a member cannot set them through the request routes (check before relying on that). (b) Or the restore moves the files: rewrite the renumbered row's ticket-folder keys to the new number's folder and have "Put the files back" place those objects at the rewritten keys, keeping a from → to key map (the restore page and `app/api/admin/restore/**` — admin-and-org — would carry the map). (c) Or a one-off server action that moves a renumbered request's files to its new folder, recorded. For the holder side, (a) alone is not enough: the holder's checks must accept a key under the shared folder only if it is listed on the holder itself (or refuse a key listed on a request whose `metadata.restore_renumbered.from` equals the holder's number). (b) and (c) close both sides, since the folder then belongs to the holder alone.

**Done when.**
- A request restored under a fresh number can have its own listed files printed or downloaded through the server copy path and named in a submit or redline, exactly as before the restore; or the integrator rules the limitation accepted and this record says so.
- A test restores two carriers of one number, the second with files, and drives one of the second's files through the server copy path and the workflow file check.
- The request that keeps the old number cannot attach, as its own, a file listed on the renumbered request (a key under the shared folder it does not list), and a test drives that refusal through `vetTicketAttachment` (*added at the P16 fix pass 4, from the review*).
